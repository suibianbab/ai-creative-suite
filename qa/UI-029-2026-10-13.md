# UI-029：PhotoCraft 工作台编辑上下文

日期：2026-10-13；本机 Next 页面与 PhotoCraft 0.6.0 桥接。

## 已验证

- 浏览器打开 `photocraft-hat-teal` 本地项目，工作台显示 1254 × 1254、3 图层和当前 `Brightness/Contrast 1` 图层。
- 输入“将整张图片顺时针旋转90度”，解析后生成真实 PhotoCraft 编辑预览；页面显示“编辑预览（未应用）”及质量确认项。
- 在预览未应用时打开 `gray-ear-refined`。旧计划、预览和应用按钮立即消失；新项目加载后显示 1920 × 2560、2 图层和当前 `Hue/Saturation 1` 图层。
- 点击 PhotoCraft 画布后，工作台提示状态待同步，解析按钮禁用，并出现“保存并同步画布”。
- Web TypeScript 检查与回归索引结构检查通过。
- 使用独立的 `ui029-workbench-20261013.png`（8 × 8）测试项目：PhotoCraft Web 内 `Ctrl+J` 复制 Background，保存后工作台显示 `Layer 1` 和 2 图层。整图旋转 90° 经预览、质量确认、应用后保存为第 4 版；从本浏览器项目重开，仍显示 2 个可编辑图层。
- PhotoCraft Web `Select → All` 后保存并未保留活动选区；CLI 对同一文档保存 `.pcraft` 与 PSD 的对照也证明：`.pcraft` 有 `[200,100,80,80]` 选区，PSD 重开则无选区。工作台现禁用无选区时的“原生源文件中的选区”选项，并明确引导用户在工作台画框/轮廓或导入含选区的 `.pcraft`。
- 另外导入了带 `[200,100,80,80]` 选区的原生 `.pcraft`：工作台显示对应范围并自动选择“使用原生源文件中的选区”；“将选区亮度提高10”由 PhotoCraft 成功生成局部可编辑预览，随后取消，未改动源项目。
- 项目打开与预览检查增加上下文版本守卫：先前请求晚返回时，不能覆盖当前图层和预览。应用前也再次确认当前项目、画布与预览属于同一上下文。
- 使用开发专用的 `mock-delayed-ollama.mjs` 返回有效亮度计划并故意延迟 3 秒：正常输入会产生“整图亮度提高 10”；请求未返回前把指令改成旋转后，旧计划没有出现。大图 PhotoCraft 旋转预览执行中把指令改为翻转，晚返回的旧预览也没有出现应用入口。
- 快速切换两份大图时复现一次桥接并发导致的 `Failed to fetch`。项目载入现设置忙碌状态，期间禁用文件与项目切换；重测载入时按钮保持禁用，完成后图层、尺寸和预览正确恢复。上下文版本检查继续处理仍可能晚返回的请求。
- 用户在独立浏览器标签完成云端登录后，云端列表显示 `hat-black-v2` 第 2 版。打开本地 `ui029-workbench-20261013` 第 4 版（8 × 8、2 图层、当前 `Layer 1`），解析“整张图片亮度提高10”并生成“编辑预览（未应用）”。未应用时直接打开云端 `hat-black-v2`：旧计划、预览、质量检查与应用入口均消失；新项目显示 1254 × 1254、2 图层、当前 `Hue/Saturation 1`，并提示已打开云端第 2 版。没有向云端保存测试改动。

## 后续按固定用例复验

UI-029 的本地/云端项目切换、过期预览清除、图层状态及可编辑源重开已通过。延迟响应验收使用了受控测试端点，证明工作台的失效处理；真实 Ollama 在本轮返回内存不足，这属于本机模型资源问题，未据此宣称模型服务可用。PhotoCraft Web PSD 不保留活动选区是已复现的能力边界，不应再当作待通过的保存场景。
