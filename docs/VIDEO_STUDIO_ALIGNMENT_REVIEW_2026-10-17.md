## 一、对齐草案的评审意见

### 总体结论

方向可行，且优于替代方案；但草案是「7 题材 × 8 引擎」的完整矩阵，不可整体并行推进。风险不在架构方向（平台管工作流、编辑器管画布、按镜头路由，与 ADR-0012 一致），而在：两个未验证的关键依赖、一处未收敛的架构分叉、以及几处未写明的空白。

收窄首期范围的代价：交互类（Rive/Spline）和 2.5D/3D 题材交付后移，「多题材产品」对外叙事初期只讲前 2–3 类。

### 评审前提（从仓库推导，如有出入以用户纠正为准）

- 团队形态：单人开发者 + AI 代理协作（git 单用户，样片均为本机/VM 开发环境）
- 阶段：探索期——PhotoCraft 一条桥已闭环；VectorCraft/EffectCraft/FilmCraft 均未集成；无生产多租户部署
- 已验证资产：Remotion 双尺寸合成、Blender RTX 4060 渲染、Asset/版本/积分/租户基线（迁移 0001–0016）

### 草案做对了什么

1. 边界按业务能力划，不按技术分层：平台持有项目/分镜/版本/交付记录，编辑器持有图层/关键帧内部格式，适配层隔离——避免第二套平行编辑器（ADR-0012 核心教训）。
2. 跨边界传值不传操作：共享素材、镜头状态、预览、交付记录，不统一内部格式。
3. 验收按样片不按 Phase：每类一条端到端样片 + 三态标注（已实现/仅样片验证/规划中）。
4. AI 视频定位诚实：「候选镜头 + 人工审片 + 单镜头重做」，不承诺全自动成片。

### 核心风险（按严重度）

- **R1 EffectCraft/FilmCraft 成熟度是最大单点赌注。** 上游自评：EffectCraft「尚不能替代商业项目的 After Effects，Windows 交互有已知问题」；FilmCraft 自评 alpha、ready for real work ~56%（2026-10-10 实测口径）。FilmCraft 官方 README 已说明每次发布附带 WebAssembly 浏览器构建（`filmcraft-web`），但「有 Web 构建」不等于「本项目已验证嵌入」——后者仍是未验证风险。约 3 个题材的主路径押在这两家，草案只说「再决定替代路径」但未列候选——悬空一格。
- **R2 云侧桥接比 PhotoCraft 更难，草案未提。** PhotoCraft 教训：「本机开发桥接，不是生产多租户任务服务」。视频引擎更重（桌面应用、GPU 渲染、大文件）；Cloud/Enterprise/AirGap 下的部署/沙箱/积分是高一档问题，开放问题清单里缺席。
- **R3 成片编排 FilmCraft vs Remotion 分叉悬而未决。** 决定适配层形状与 UI 主时间线归属；不预定标准容易变成两条时间线都养着——恰是草案要避免的。
- **R4 单人团队 × 8 条引擎桥的集成面。** PhotoCraft 一条桥（含质量环、批量线、grounding 评测）消耗数周；草案未内嵌时序约束，评估文档的「近期验证顺序」未被引用。

### 优化点

1. **平台脊柱与引擎桥解耦成两条独立验证线**：项目/分镜/镜头状态/版本/资产层用已验证引擎（HTML/GSAP/D3 → Remotion，Blender）先跑通端到端样片；EffectCraft/FilmCraft 桥验证并行推进。平台 schema 设计压力与引擎成熟度风险互不绑架。
2. **给每个待验证候选预写降级路径**：EffectCraft 不可用 → 传统动效由 HTML/GSAP + Remotion 承接（质量上限降低但可交付）；FilmCraft Web 嵌入不可行 → 桌面应用 + 文件交接的半自动桥，或暂缓剪辑题材。
3. **Storyboard/镜头 schema 是唯一重不可逆决策，单独 ADR + 最小集设计**：v1 只为前 2–3 个题材设计字段；重点设计镜头版本 ↔ 引擎源文件引用 ↔ 渲染产物绑定（复用不可变版本、requestKey 幂等模式）；补定义镜头状态机（draft → candidate → approved → locked → exported，谁可转换、锁定后禁哪些操作）。
4. **FilmCraft vs Remotion 提前定决策标准**：约束是「**每个交付版本只有一条权威终片时间线**」——镜头素材可以来自多个引擎，但同一交付的终片编排权只归其一（按该项目的编辑需求选 FilmCraft 或 Remotion）；另一引擎只能作为素材来源，不得形成并行的记录级时间线。写成 ADR（决策点 D3），用一条混合素材样片（程序化镜头 + 实拍镜头同片）验证交接后确认或推翻。
5. **镜头路由层防过度设计**：让适配器接口从最先落地的 2–3 个桥长出来（PhotoCraft 桥已给出模式：版本锁定、保存/重开校验、golden check、命令注册表同步）；路由 v1 就是一张「内容类型 → 引擎」查表。
6. **补四块空白**：音频生产（旁白 TTS/录音、音乐版权、混音——数据/STEM 与教程题材硬依赖，无引擎认领）；字幕/转写（ASR，FilmCraft 未必自带）；渲染与预览策略（镜头级 vs 整片预览；云侧 GPU 队列无着落）；版本存储增长（渲染产物 + 原生工程大，孤儿清扫要扩展到渲染产物）。
7. **验收样片分层**：Tier 1 文字/数据动效（验证平台脊柱）；Tier 2 FilmCraft 剪辑（验证编辑器集成）；Tier 3 2.5D/3D/AI 叙事（资产重）；交互类明确延后单独立项。

### 草案第 5 节六问答复

| # | 问题 | 答复 |
|---|---|---|
| 1 | Video vs Motion Studio | 对外用 Video Studio（视频是主要交付物）；交互类标注为独立交付类型。可逆决策，不多花时间 |
| 2 | 控制粒度 | 粒度对；缺镜头状态机定义，建议补 |
| 3 | EffectCraft/FilmCraft 首选 + 桥样片后定集成 | 原则正确，必须预写降级路径 |
| 4 | 程序化/交互作为独立交付类型 | 是；与「不用 MP4 冒充状态机」一致 |
| 5 | AI 视频「候选+审片+单镜头重做」 | 接受；补积分/成本预估展示（复用 Credit Ledger） |
| 6 | 质量门槛 | 大体合理；每类样片模板加「能力上限声明」栏，把「通过」和「未测的上限」分开 |

## 二、SVGAnimate 对标结论（2026-10-17 实测）

SVGAnimate 实际功能：两种模式（HTML Video 多场景解说视频 / SVG 单场景动画，下分 STEM、地图、数据可视化、3D、火柴人、文字、Logo、产品演示、流程图、Loading、手绘、交互、线描、Web 小游戏、动态网页 15 类）；一句话 → agent 扩写脚本和分镜 → 逐场景可调 → 导出 SVG/GIF/MP4/HTML；有 Gallery、会员定价；无 API；自声明「代码生成适合几何/矢量视觉，不适合写实图像」。

**覆盖判断：对标范围全部有拟定路径，全部未经样片验证。** SVGAnimate 是六个参考中路径最顺的一个——它的能力面基本落在本方案的程序化 HTML/SVG/GSAP/D3 路线上，不依赖任何未验证编辑器桥。但「路径拟定」不等于「可实现性已证明」：本项目 Remotion 样片（form01）是手写固定合成，尚不能证明任意生成场景能稳定逐帧确定性渲染。覆盖状态按三类口径标注（当前全部为「路径拟定」）：

| 矢量子类（11 个，逐项见下表） | 组件注册表 + scene_spec | 路径拟定（P0–P2，逐项见下表） |

**效果判断（对标判断，非实测结论）：**
- 预期可达到：矢量动效本体（同技术路线；确定性渲染设计为按帧纯函数，优于其浏览器录屏回退——此为设计目标，待 P0 fitness function 实测）。
- 结构性优势（设计层判断，待样片）：写实内容（PhotoCraft 真实图片、Blender 写实 3D、AI 视频候选——对方自声明做不到）；可编辑源更深；多尺寸交付。
- 初期可能落后三处：一键生成便利度（单路径打磨 vs 宽平台）、TTS 旁白+字幕链路（其内置，我们未认领引擎）、Gallery/模板内容库（冷启动工作量）。
- 两个无既有基础的新环节：① TTS 旁白与字幕对齐（决策点 D2）；② **生成场景的沙箱执行与帧确定性渲染**（ADR 0003 §2 执行边界——声明式 scene_spec + 版本化组件注册表 + 资源限制 + 双渲染帧哈希 fitness function）。两者都是 P1 前必须验证的能力，不是已验证资产的迁移。

## 三、功能实现优先级（SVGAnimate 优先路线）

### 路线原则

1. SVGAnimate 的**矢量子类**由组件注册表按子类扩展覆盖（ADR 0003 声明式边界：新视觉能力 = 新注册组件，不是自由代码生成）；开放式网页动画、交互与小游戏**不假设由同一组件集自然覆盖**，走独立交互交付路径（P3，保留可运行源，不经成片渲染）。全程**零新编辑器桥**，风险最低。
2. 平台脊柱（项目/分镜/版本）用已验证引擎先跑通；EffectCraft/FilmCraft 桥验证为并行支线，不阻塞主线。
3. 验收沿用草案 §4：每阶段以端到端样片收口，qa registry 登记，三态标注。

### 优先级表

| 阶段 | 内容 | 复用资产 | 收口样片 |
|---|---|---|---|
| **P0 平台脊柱 + 单场景出片闭环** | 镜头/分镜数据模型按 [ADR 0003](adr/0003-video-studio-shot-schema.md) 实施（内容版本/审批事件/渲染记录三分、lineage、duration_ms 量化）；Video Studio 工作台壳与项目列表；一句话→脚本+分镜计划（IR/硬校验/确认环）；场景渲染框架 v1 = 声明式 scene_spec + 版本化组件注册表（文字动画、线描、基础图形），渲染按帧纯函数、禁网络/墙钟、资源限额；Remotion 横竖版 MP4 导出 | 云项目/版本/幂等的实现模式（VideoProject 需新校验+存储+迁移，不直接复用 image_projects）；PhotoCraft NL M1–M4 方法论；Remotion 引擎包 | 一句话生成 10–15 秒单场景文字/线描动画，横竖版 MP4，分镜 JSON 与场景源可保存重开；**同输入集双渲染解码帧一致**（确定性 fitness function；输入集 = spec + 组件版本 + 资产/字体摘要 + 渲染器/浏览器版本 + 输出参数，全部记录进渲染记录） |
| **P1 HTML Video 完整链路** | 多场景编排（转场、时序、整片预览）；TTS 旁白 Provider 接入；字幕轨（脚本驱动、时间对齐、可编辑）；分镜编辑器（逐镜头调画面/旁白/字幕、单镜头重做）；导出扩充 GIF、单场景 SVG 文件 | Credit Ledger 计费；镜头版本模式；千问 Provider 路由经验 | 一句话→多场景 STEM 旁白解说视频，画面/旁白/字幕逐场景可调，横竖版 MP4（即 SVGAnimate HTML Video 对标样片） |
| **P2 题材模板扩展** | 数据可视化（D3 图表+数字滚动）、地图动画、流程图/示意图、火柴人/手绘/Loading 风格；每题材首批 3–5 个起点模板 | P0/P1 场景框架 | 数据、地图、流程图、火柴人、手绘、Loading 各一条样片；P2 收口累计覆盖 11 个矢量子类中的 9 个（P0 文字/线描 + P1 STEM + P2 新增 6 类）；Logo 动画与产品演示为候选未排定，不计入覆盖承诺 |
| **P3 交互与 3D** | 交互动画/动态网页（HTML 交付、事件/状态、可嵌入）；Three.js 3D 场景；小游戏（可选） | 浏览器交互路线 | 交互交付物实际触发+嵌入（不以 MP4 充数） |
| **P4 产品化与体验** | Gallery、提示引导、一键流程打磨、计费对齐；Logo/品牌动效增强（此时决定是否引入 EffectCraft 桥） | Credit Ledger；qa registry | Gallery 上线；一键流程可用性样片 |

### 并行支线（不阻塞主线）

EffectCraft 非商品动效桥样片、FilmCraft 剪辑桥样片——按 `CRAFT_APPS_REUSE_ASSESSMENT.md`「近期验证顺序」执行；失败走优化点 2 的预写降级路径。

- **D1** 镜头 schema ADR（P0 开工前）——已完成：[ADR 0003](adr/0003-video-studio-shot-schema.md)（Codex 审核修订 + 用户确认四项开放问题，状态 accepted）

- **D3** Remotion vs FilmCraft 终片分工 ADR（FilmCraft 样片后或 P4 前）
- **D4** GIF 导出工具链（P1 中，如 ffmpeg palette）

| 质量纪律 | qa registry + 样片验收 + 三态标注流程 | 直接复用 |
| 优势项：写实素材 | Blender RTX 4060 样片、PhotoCraft 图片编辑、AI Provider 路由 | 均为技术样片，未进入视频工作流 |

**两个无既有基础、必须 P1 前验证的新环节**：① TTS 旁白与字幕对齐（决策点 D2）；② 生成场景的沙箱执行与帧确定性渲染（ADR 0003 §2）。两者量级仍小于任何编辑器桥，但不能再表述为「已验证资产的迁移」。
